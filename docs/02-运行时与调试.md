# 运行时行为与调试手册

> English: [02-runtime-and-debugging.md](en/02-runtime-and-debugging.md)

本文记录把 QGIS 桌面版跑在浏览器里时实际踩到的问题、原因和处理方式。所有结论都来自 `tests/e2e/*` 在 Chrome 149（headless + SwiftShader）上的复现。

## 1. 启动流程

```
index.html ─ qtloader.js ─▶ qgis.js (MODULARIZE, EXPORT_NAME=qgis_entry)
   │  qt.environment: QGIS_PREFIX_PATH=/qgis  PROJ_DATA=/proj  HOME=/home/web_user
   │  preRun: FS.mount(IDBFS, /home/web_user) + FS.syncfs(true)          ← 用户目录来自 IndexedDB
   │  qgis.data (19 MB) → /qgis/share/qgis/{resources,svg,fonts}, /proj, /qgis/share/demo
   ▼
main()  (QGIS 自己的 src/app/main.cpp)
   ├─ Q_INIT_RESOURCE(images)        静态库里的 Qt 资源（图标、启动画面、符号 SVG）必须显式引用
   ├─ QgsApplication myApp(...)       QGIS_PREFIX_PATH → pkgDataPath=/qgis/share/qgis
   ├─ fontManager()->addUserFontDirectory(<data>/fonts)   Open Sans（默认样式使用）随包提供
   ├─ setMaxThreads(8)                每个 QThread 都是一个 Web Worker
   ├─ 设置默认值：不下载字体、不拉取 feed.qgis.org（浏览器 CORS 会拦）
   ├─ QgisApp  ── 真正的 QGIS 主窗口 ── showMaximized() + 显式设成屏幕（页面）尺寸
   ├─ completeInitialization()  →  sQgisWasmReady = true
   └─ QgsApplication::exec()    主循环通过 JSPI 挂起/恢复，main() 永不返回
```

本机（32 核、tmpfs 浏览器档案）上：页面可交互约 2 s（wasm 实例化），QGIS 主窗口约 8 s，打开 demo 工程并完成并行渲染约 10 s；换成 12 核机器、Chrome 149 实测主窗口 2.4 s、demo 渲染 10 s（性能差异见 docs/06 §7）。

## 2. 关键发现

### 2.1 JS → C++ 的调用必须排队进 Qt 事件循环

Qt for WebAssembly 的主事件循环在两次事件之间处于 **JSPI 挂起** 状态。如果 JavaScript 直接调用一个 C++ 导出函数，而这段 C++ 又在另一条栈上触发了挂起（嵌套事件循环、`QProgressDialog`、`processEvents(WaitForMoreEvents)`……），Qt 的 `QWasmSuspendResumeControl` 只记录一个挂起点，主循环从此再也收不到恢复信号——表现为：JS 仍然活着、Qt 定时器全停、不再重绘、页面"冻住"。

`qgis_wasm_open()`（`src/app/qgswasmapp.cpp`）因此只做一件事：`QMetaObject::invokeMethod(app, [...]{ app->openFile(path); }, Qt::QueuedConnection)`，由 Qt 自己的循环在 `processEvents()` 里完成真正的工作。`ccall` 也无需 `async`。**所有以后新增的 JS 入口都要遵守这一规则。**

同样的规则适用于一切**从 JavaScript 回调进入的 C++**，不只是导出函数：Qt wasm 的 `QNetworkReply::finished` 是从浏览器 fetch 的回调里同步发出的，在这个槽里直接跑会开嵌套事件循环的代码（`QgsBlockingNetworkRequest` 下载、对话框）会让 QGIS 整个冻住。`QgsWasmAssistantDock` 因此把每个网络回复先 `QMetaObject::invokeMethod(..., QueuedConnection)` 排进 Qt 事件循环再处理（第一版没这么做，助手调用 `layers_add` 下载数据时就冻住了）。判断方法：问自己"这段 C++ 的调用栈最底下是 Qt 的 `processEvents()` 还是某个 JS 回调"。

### 2.2 页面自己的 UI 与 Qt 的全局事件监听

Qt for WebAssembly 把指针事件挂在 `window`（capture）、把 `keydown`（capture）和 `copy/cut/paste` 挂在 `document` 上，并在处理时 `preventDefault()`。结果是页面层的输入框（工作区、agent 的聊天框）点一下不会获得焦点、Ctrl+V 永远不会粘贴——e2e 用 `fill()` 程序化聚焦所以一直没发现。`workspace.js` 在 Qt 启动前包装了 `window/document.addEventListener`：此后注册的这类监听器，遇到目标在 `.ws-root / .ws-menu / .qa-root` 里的事件直接跳过；页面自己想全局生效的监听器（Ctrl+Shift+Space）标记 `__wsPassthrough`。Shadow DOM 里的 Qt 画布事件在 window 层已被重定向到宿主元素，不受影响。`features.py` 用真实点击 + 剪贴板权限回归。

### 2.3 "从电脑选文件就挂了"：是页面层盖住了 QGIS，不是对话框

现象：Data Source Manager 里的 "…"、"Load"、甚至右下角的 "Close" 点了没反应，应用其它部分正常。排查时先怀疑 QFileDialog（从次级窗口的输入回调里开嵌套事件循环）：加了 `ui_debug_dialog` 诊断工具对比后，文件对话框从主循环、从任意父窗口、带不带 QGIS 那串 2886 字符的矢量格式过滤器都能正常弹出；给 `QgsFileWidget::openFileDialog()` 加日志后发现点击根本没进到槽函数。`document.elementFromPoint()` 给出答案：工作区关闭时卡片 `opacity: 0; pointer-events: none`，但嵌在里面的 agent 面板自己写了 `pointer-events: auto`——子元素的 `pointer-events` 不受父元素 `none` 约束——于是一张看不见的卡片吃掉了屏幕右侧约三分之一的全部点击。修法：`workspace.css` 对关闭态的 `.ws-panel` 及其所有后代强制 `pointer-events: none !important` 并 `visibility: hidden`，agent 面板改为 `pointer-events: inherit`；`agent.py` 用 `elementFromPoint` 回归。教训：页面层任何覆盖在 QGIS 画布上的元素，关闭时必须整棵子树失活；排查"QGIS 某块区域点不动"先用 `elementFromPoint`。`ui_debug_dialog`（`kind: file | static | staticfilter | plain`，`parent: main | active | none`）留作诊断工具。

### 2.4 线程池要预加载并且要有上限

QGIS 的并行渲染（`QgsMapRendererParallelJob`）每层一个线程，还有任务管理器、浏览面板扫描等线程。Emscripten 的 Worker 池默认懒加载（`PTHREAD_POOL_DELAY_LOAD=1`），每个 Worker 第一次用到时才去实例化 130 MB 的模块，而 QGIS 在不少地方会 **同步等待** 渲染线程（取消任务、`waitForFinished`）——主线程一等，Worker 的加载就卡住。现在：

- `PTHREAD_POOL_DELAY_LOAD=0`，池大小 `clamp(hardwareConcurrency, 8, 16)`，启动时全部就绪；
- `QgsApplication::setMaxThreads(min(idealThreadCount, 8))`。

### 2.5 静态链接带来的差异

| 现象 | 原因 | 处理 |
|---|---|---|
| 所有图标 `:/images/...` 找不到 | `images.qrc` 编进 `libqgis_core.a`，没人引用就被链接器丢掉 | `main.cpp` 里 `Q_INIT_RESOURCE(images)` |
| 欢迎页 QML：`module "org.qgis.app" plugin "qgis_appplugin" not found` | QGIS 用 `Qt::` 无版本名链接，`qt_import_qml_plugins` 走不到依赖 | `QgisWasmApp.cmake` 显式链接 `qgis_appplugin` + `qgis_appplugin_init` |
| `duplicate symbol tinygltf::...`、`_GEOSQueryCallback` | 两个库各编了一份实现 | 补丁：静态构建只保留一份 / 改 `static` |
| `QgsAuthManager::passwordHelperDisplayName` 等未定义 | gui 用到的 auth 数据类只在 `WITH_AUTH` 下编译 | core 在无 auth 时也编译 `qgsauthconfig.cpp`、`qgsauthmethodmetadata.cpp`，补两个 stub |
| QScintilla `RunStyles<long,...>` 未定义 | wasm32 上 `ptrdiff_t` 是 `long`，Scintilla 以为等于 `int` 就不实例化 | port 补丁 |

### 2.6 设置

QGIS 4 的 `QgsSettingsEntry*`（新式设置 API）**只读用户配置文件**，不看 `qgis_global_settings.ini`（后者只对旧式 `QgsSettings` 键有效，例如 `qgis/checkVersion`）。所以"不下载缺失字体"、"关闭新闻源"这类浏览器部署默认值在 `main.cpp` 里用 `exists()` 判断后写入一次，用户之后仍可在选项里改回去（配置在 IDBFS 中持久化）。

### 2.7 其它运行时行为

**文件与路径**

- **工程必须带 `<mapcanvas>`**。PyQGIS 无界面写出的工程没有画布范围，`QgsMapCanvas` 认为设置无效、什么也不画（原生 QGIS 同样如此）；`scripts/make-demo-project.py` 会补上。
- **文件对话框不是浏览器的那个**。Qt wasm 的"原生"文件对话框其实是浏览器的文件选择器/下载，`QFileDialog::getSaveFileName()` 直接返回空字符串，Project → Save As… 就什么也不发生。`main.cpp` 在 Emscripten 下设置 `Qt::AA_DontUseNativeDialogs`，改用 Qt 自己的对话框，浏览的是虚拟文件系统，文件名框里可以直接输入绝对路径。
  - 保存到不存在的目录会失败（和桌面一样）：先用对话框的"新建文件夹"，或存到已有目录；`project_share` 会自动建目录。
  - 左侧书签由 `QgsWasmPreset::apply()` 预填：preset 的 `mounts` → `/cloud/<name>`，加上 `favorites`、`/cloud`、`/home/web_user`、`/qgis/share/demo`，只加存在的目录，用户自己加的书签保留。
  - 书签写在 `QSettings( UserScope, "QtProject" )` 的 `FileDialog/shortcuts`，另外必须写 `sidebarWidth`：没有它，`QFileDialogPrivate::restoreWidgetState()` 会因为空的 splitter 状态提前返回，书签根本不会生效——这就是先前预填 `~/.config/QtProject.conf` 看起来"无效"的原因之一。
- **云挂载的文件 I/O 是同步 XHR**（`cloudfs.js`）。Emscripten 文件系统在主线程，工作线程的 `read()` 会被代理到主线程，所以请求在主线程上同步完成；主线程的同步 XHR 只能以 `x-user-defined` 文本收二进制。大文件首次读取期间 UI 会卡住：≤ 16 MB 整文件取，更大的按 4 MB 块按需取；写入在 `close()` 时整体 `PUT`。

**设置与持久化**

- **设置存在 `window.localStorage`，不是 `.ini` 文件**。`QgsUserProfile::initSettings()` 在 Emscripten 下不调用 `QgsSettingsEntryBase::setupUserSettings()`（它会 `QSettings::setDefaultFormat(IniFormat)` + `setPath(profile)`，而文件式 QSettings 依赖 QLockFile/QSaveFile，在 wasm 上不可靠），于是 Qt 用 wasm 的 `NativeFormat` = `WebLocalStorageFormat`。
  - 每个键一条记录，前缀 `qt-v0-<org>-<app>-`：QGIS 自己是 `qt-v0-QGIS-QGIS4-`，文件对话框是 `qt-v0-QtProject-all-apps-`。
  - 写入即落盘、刷新页面仍在，与 IDBFS 无关。调试时在控制台看 `Object.keys(localStorage).filter(k => k.startsWith('qt-v0-'))`。
  - "重置配置" = 清掉这些键，再加 IndexedDB 里的 `/home/web_user`。profile 目录（`/home/web_user/.local/share/QGIS/QGIS4/profiles/default`）里只有 qgis.db、symbology-style.db 等数据库，没有 QGIS4.ini。

**窗口、字体与首帧**

- **窗口**：Qt wasm 的顶层窗口画在 shadow DOM 里（`#qt-shadow-container` 的 shadowRoot，每个窗口一个 `<canvas>`）；模态对话框是独立窗口（`canvases` 数量 +1）。
- **标题栏与第一帧**：Qt wasm 会给每个有边框的顶层窗口画自己的标题栏和边框。主窗口就是整个页面，所以 `qgis-shell.js` 往 shadow DOM 注入样式，把最大化窗口的整条标题栏和边框去掉。
  - 没有边框边距时 Qt wasm 不会把尺寸传给 QWidget，因此 `QgsWasmApp::showMainWindow` 在显示后 0 ms / 1000 ms 以及每次页面尺寸变化时显式 `setGeometry`（web agent 面板停靠、页面变窄就靠这个）。
  - `QgisApp` 构造函数会恢复桌面上的窗口几何，浏览器里没有存档，默认落到"屏幕 80%、偏移 10%"——这一帧先被画出来、再被最大化，就是曾经看到的"左上角一个小窗口再铺满"。
  - 试过的替代方案：`Qt::FramelessWindowHint` + 显示前设好几何，第一帧确实是整页，但欢迎页的 QML 视图停在最小尺寸不再恢复（Qt wasm 不给它发 resize），所以放弃。
  - 现在的做法在页面层：`onLoaded` 时给加载页加一个**不透明的 hold**（`qgisLoading.hold({ opaque: true })`），桥接就绪且 ≥ 2.5 s 后才释放（上限 6 s），中间帧都发生在加载页后面；带 `?share= / ?open=` 的链接之后接着用半透明的幕继续。
- **字体**：Qt wasm 内置 DejaVu Sans/Mono；默认样式用的 Open Sans 以静态 TTF 随包提供（可变字体会被 FreeType 拒绝）。放在 `web/fonts/` 的任何 `.ttf/.otf` 都会被 `addUserFontDirectory` 装载。

**网络与线程**

- **网络**：`QNetworkAccessManager` → 浏览器 fetch，受 CORS 限制。`?open=https://…` / `window.qgisOpen(url)` 先 `fetch` 到 `/home/web_user/downloads/` 再交给 `QgisApp::openFile()`，所以 GDAL/OGR 读的是本地文件，不受 `/vsicurl/` 缺失影响。
- **User-Agent**：浏览器禁止页面设置 `User-Agent` 请求头，`QgsNetworkAccessManager` 在 Emscripten 下不再设置它（否则每个请求刷一条控制台错误）。
- **JS → C++ 工具调用**：`qgis_wasm_call(id, tool, json)` 只排队（§2.1 的规则），`QgsWasmBridge::callFromJs` 在事件循环里执行并通过 `Module.qgisBridgeResolve` 回传。
- **主线程上不能用 `QgsBlockingNetworkRequest`**：实测它的嵌套事件循环在这个运行时里不会让出（连页面的 JS 定时器都停了），整个标签页卡死。所以 `files_download` / `layers_add(URL)` 用 EM_JS 里的同步 XMLHttpRequest 直接写进虚拟文件系统（和 cloudfs 一样），助手和 MCP 客户端全部用异步的 `QNetworkAccessManager`。

**缓存**

- **`qgis.js` 与 `qgis.wasm` 必须成对，且都不能被缓存成旧版**。胶水 JS 里的 `ASM_CONSTS` 表按二进制里的代码地址索引；重编后浏览器若还拿着旧的 `qgis.wasm`（或旧的 `qgis.js`），`main()` 一进 `QCoreApplication` 就报 `ASM_CONSTS[code] is not a function`（在 `QWasmSuspendResumeControl` 里），页面什么都不显示。
  - `scripts/serve.mjs` 对所有静态文件发 `Cache-Control: no-cache` + `ETag`/`Last-Modified` 并处理 `If-None-Match` → 304：每次加载都校验，但不重新下载 130 MB。
  - 用别的静态服务器部署时同样要么开 ETag 校验（nginx：`etag on; add_header Cache-Control no-cache;`），要么把两个文件改成带内容哈希的文件名。用户侧的临时办法是 Ctrl+Shift+R 强制刷新。

| "worker sent an error! qgis.js:1: Uncaught RuntimeError: table index is out of bounds"（随后一条 "Uncaught [object ErrorEvent]"） | 某个 pthread（渲染线程 / 任务线程）里的 wasm 陷阱：间接调用的函数表下标越界——通常是野函数指针（释放后使用的虚表、线程间的数据竞争），只打断那一个线程，主窗口照常。浏览器只把 message / 文件 / 行号交给页面，Error 和栈留在 worker 里，光凭这一行查不出来。页面因此给每个 `em-pthread` worker 套一段两行的 blob 前导（`debug.js`）：在 worker 内部监听 `error`，把带函数名的 wasm 栈（构建保留 `--profiling-funcs`）经 BroadcastChannel 转到 Debug 视图，条目形如 `worker #3 (pthread 0x…) crashed: RuntimeError: … at QgsMapRendererParallelJob::…`。再遇到时：Debug 视图 → `qgis` 过滤 → copy，把那一条连栈发出来即可定位。**后果**：线程一崩，Emscripten 会给主线程打上标记（`_emscripten_thread_crashed`），主线程下一次等锁（`emscripten_yield`）时抛出字符串 `"unwind"`，把当时栈上的 C++ 全部撕掉——所以之后的工具调用会报 `Error: unwind`、或者排进队列再也没有回音，画布也不再刷新（"样式设完没反应"多半就是它）。页面因此把崩溃当成一个状态：`window.qgisCrash`、事件 `qgis-crash`，页顶出现红色横条（Reload / Debug view / Copy report），`qgis.call` 把 `unwind` 和之后的无回音统一改报 "QGIS is no longer usable in this tab… reload"（agent 看到这句就停，不再重试），崩溃报告存进 localStorage，重载后 Debug 视图第一条就是 "previous session … crashed"，随时可 copy |
| 工具调用报 `Error: unwind` / 排队后没有回音 / 改样式后画布不动 | 见上一行：这是某个 worker 线程早先崩溃的后遗症，不是那个工具的错。页顶应有红色崩溃横条；没有的话看 Debug 视图里有没有 `worker #N … crashed`。唯一的恢复办法是重新加载页面 |
| "分享完卡住 / 打开分享链接没反应" | 曾经的原因：`cloudfs` 为了给 QGIS 同步的文件系统语义用的是**同步 XHR**，分享时 9 MB 的 GeoJSON 在主线程上同步 PUT、打开时同步分块 GET，标签页整段冻结且画不出进度。现在分享在 write-behind 租约下写入、异步并行上传；打开快照先异步预取（按 key 直达，不列目录；`GDAL_DISABLE_READDIR_ON_OPEN=EMPTY_DIR` 省掉 GDAL 打开文件时的目录扫描）。仍会短暂占用主线程的是 QGIS 自己的 CPU 工作：`layer_set_source` 让 OGR 重新解析大 GeoJSON、保存工程——进度条上会写明"QGIS re-reads …"。快照里的 GeoJSON 现在打包成 GeoPackage（docs/06 分享一行）：重读和之后每次渲染读的是带空间索引的 SQLite，而不是整份 JSON |
| 浏览器控制台 `qgis.call('state')`、`qgis.tools()`、`qgis.on('*', console.log)` | 直接操作控制面、观察事件 |
| `curl -X POST http://127.0.0.1:8123/agent/call -d '{"tool":"layers_list"}'` | 不经 MCP 直接调用页面里的 QGIS |

## 4. 已知限制 / 后续

- **内存上限 4 GiB（wasm32）**：堆初始 512 MB、按需增长到 4 GiB（`MAXIMUM_MEMORY=4GB`，这是 32 位 wasm 的硬顶），且只增不减。消息栏出现 "<图层名>: Insufficient memory for image W×H" 表示那一帧给该图层分配画布时堆增长失败（到顶或浏览器拒绝扩容），该层这一帧不画、不会崩。突破需要 Memory64（wasm64）：Emscripten `-sMEMORY64=1`、全部依赖重编、Qt wasm 平台插件/loader 的 JS 胶水 64 位化（指针变 BigInt）、JSPI+线程+Memory64 组合未验证、性能约慢 10–20%、Safari 不支持——评估为数天到两周且结果不保证，目前不做。先做的替代：渲染线程调低、图像缓存调小、cloudfs 大文件按块缓存。

- 启动需要下载约 152 MB（`qgis.wasm` 133 MB 含函数名 + `qgis.data` 19 MB）；Release 不带 `--profiling-funcs` 可再小 15 MB，静态资源可改为按需 `fetch`。
- 没有 Python、没有 SSL 证书管理、没有 3D；`/vsicurl/` 不可用（GDAL 未编 curl），远程文件由 `layers_add`/`files_download` 整体下载，或通过 `/cloud` 挂载按块读取。
- 浏览面板里的 "Home"、"/" 等目录项扫描的是 MEMFS/IDBFS，"Cloud" 收藏夹扫描的是对象存储（每个目录一次 ListObjectsV2，缓存 30 s）。
- 文本框 IME、剪贴板、拖放依赖 Qt wasm 平台插件的实现程度。
