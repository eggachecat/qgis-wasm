# 架构与分层：壳层做什么、QGIS 不做什么

> English: [06-architecture.md](en/06-architecture.md)

这个仓库里跑在浏览器里的是真正的 QGIS 桌面版。它的外面是一层很薄的**页面壳（`web/shell/`）**，再外面是独立的 **Web Agent（`web/agent/`）**。分层的原则只有一句话：

> **QGIS 只认识文件和工具调用。URL、分享、preset、云存储协议、外部数据服务、模型——全部在页面层。**

这样做的收益是直接的：换一个对象存储、接一个新的内部数据服务、改分享链接的格式、换模型，都不碰 C++，不重新编译（25 分钟），刷新页面即生效；升级 QGIS 版本时，补丁只有一个小而稳定的工具面（docs/05 §3）。

```
┌──────────────────────────────────────── 浏览器页面 ────────────────────────────────────────┐
│                                                                                              │
│   web/agent/            web/shell/（壳层：页面侧的"产品"）                QGIS (wasm)        │
│   ┌─────────────┐       ┌──────────────────────────────────────────┐    ┌────────────────┐  │
│   │ 模型循环     │       │ index.html   预检（JSPI / SAB）→ 按序加载   │    │ QgsWasmBridge  │  │
│   │ 技能 / MCP   │──────▶│ qgis-shell.js  preset、window.qgis、插件、  │───▶│ ≈50 个工具      │  │
│   │ 面板 UI      │ 工具  │                SSE/MCP 传输、启动编排        │工具│ (C++, 只增不改) │  │
│   └─────────────┘ 契约  │ link.js      URL 方案：?open ?add ?extent …  │调用│                │  │
│                         │              view_link / Share 菜单          │    │ QgsWasmPreset  │  │
│   agent.html?qgis=…     │ sources.js   查询数据源：OGC API / 目录 /     │◀───│ 设置、底图、    │  │
│   （远程宿主）           │              GeoJSON API → sources_* 工具     │事件│ 收藏夹、C++插件 │  │
│                         │ cloudfs.js   对象存储 → /cloud/<name>（文件） │    │                │  │
│                         │ pyqgis.js    Pyodide + PyQGIS 兼容层          │    │ 文件系统 (FS)   │  │
│                         └──────────────────────────────────────────┘    └────────────────┘  │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
          scripts/serve.mjs：静态文件（COOP/COEP、.br/.gz 旁路文件）、/proxy（CORS）、/mcp、/agent/*
```

依赖方向：**agent → `window.qgis`（工具契约）← QGIS**；壳层内部 `link.js` 用 `sources.js`（`source://` 链接），两者都只通过 `window.qgis.call()` 和 Emscripten 的 `FS` 接触 QGIS。QGIS 侧没有任何代码引用 URL 参数、分享、数据源或 agent。

## 1. 每一层的职责

| 层 | 文件 | 知道什么 | 不知道什么 |
|---|---|---|---|
| **QGIS 内核** | `external/QGIS/src/app/qgswasm*.{h,cpp}`（补丁） | 工具注册表（`layers_add`、`canvas_set_extent`、`ui_add_action`…）、应用 preset 的 `settings/basemaps/favorites/plugins_cpp`、虚拟文件系统 | URL、分享、云存储协议、外部数据服务、模型、agent |
| **壳层：启动与契约** | `qgis-shell.js` | 加载模块、preset、`window.qgis`（QGIS 工具 + 页面工具 + 事件）、Web/Python 插件、对外的 SSE/MCP 传输 | 任何具体业务 |
| **壳层：URL 与分享** | `link.js` | `?open ?add ?basemap ?crs ?extent ?ask` 的语义；`view_link`/`project_share` 生成的链接；Plugins → Share 菜单 | QGIS 内部结构（只调工具） |
| **壳层：查询数据源** | `sources.js` | 适配器契约（`collections / search / fetch`）、内置的 `ogcapi / catalog / geojson` 三种类型、`sources_*` 工具、Plugins → Data sources 菜单、`source://` 规格 | 数据怎么渲染（写成文件后 `layers_add`） |
| **壳层：存储** | `cloudfs.js` | Swift / S3 / HTTP 目录 → `/cloud/<name>` 文件系统（SigV4、分块读、写回） | 文件内容的含义 |
| **壳层：Python** | `pyqgis.js` + `pyqgis/` | Pyodide、PyQGIS 兼容层 → 工具调用 | — |
| **壳层：工作区面板** | `workspace.js` | 页面自己的门面：按钮、头部菜单、浮动卡片 / 停靠侧栏、插件与 agent 的槽位 | agent 内部、模型 |
| **壳层：分享** | `share.js` | 快照的布局、清单、打包与刷新 | QGIS 内部（只用 `project_save`、`layer_set_source`） |
| **壳层：调试视图** | `debug.js` | 页面与 QGIS 两边的日志、耗时、卡顿、崩溃 | — |
| **壳层：任务总线** | `progress.js` | 所有耗时操作的统一进度汇报 | QGIS（它不知道有这回事） |
| **壳层：加载页** | `loading.js` + `index.html` | 真实字节数、阶段、hold、品牌 | — |
| **Web Agent** | `web/agent/` | 模型循环、技能、MCP 客户端、审批策略、三层配置、对话 UI | `window.qgisInstance`、FS、C++、壳层其它模块（只认 `window.qgis` 与 `window.qgisWorkspace`，docs/05） |
| **服务器** | `scripts/serve.mjs` | 静态文件与头、`/proxy`、`/mcp`、`/agent/*` | 页面逻辑（任何静态服务器 + 两个响应头即可替代前半部分） |

### 1.1 几个壳层模块的细节

**工作区（`workspace.js`）**

- 右下角扁平按钮打开浮在地图上的卡片，或 `ui.layout: "dock"` 改成停靠侧栏；头部菜单 Project / Share / Data / ⋯（保存、分享链接、MCP 端点、数据源与挂载、布局、链接、关于）**全部经 `window.qgis` 工具**，页面上没有第二套 QGIS API。
- 主体是一个槽位：agent 渲染进去；`window.qgisWorkspace`（`open/close`、`slot`、`addAction`、`setBadge`）是它给页面其它模块的接口。

**分享（`share.js`）**

"分享"只有一个意思：云挂载上一个**冻结、自包含的工程文件夹** `<mount>/<prefix>/<id>/`，里面是：

- `project.qgz`；
- `data/`——只存在于浏览器里的图层文件（查询结果、上传、下载、导出）；
- `share.json` 清单——标题、时间、视野、每一层的来源 `source://…` 与大小。

工具是 `project_share` / `share_open` / `share_refresh`，链接是 `?share=<id>`；刷新 = 按清单重跑查询、原地改写 `data/` 里的文件（图层 id、名字、样式不变）。

浏览器本地的 GeoJSON（查询结果）进快照时由 QGIS 打包成 **GeoPackage**（`native:savefeatures` 写到本地临时文件再拷进文件夹，`data/x.gpkg|layername=x`，清单里记 `packed: "geojson"`；刷新同样打包）。为什么值得打包：

- 有空间索引，打开即用——GeoJSON 没有索引，碰它的每个线程都要整个解析一遍；
- 体积小约 30 %；
- 实测 10 MB / 2.5 万个面：打包 0.3 s、7.2 MB；`layers_add` 0.06 s 对 0.52 s；放大后的渲染快 3–4 倍（105/45/37 ms 对 192/161/182 ms）。

打不成（混合几何、怪字段）就原样复制。传输不卡标签页：快照在 `cloudfs` 的 **write-behind 租约**下写入（文件先留在内存，QGIS 重读、保存工程都从内存走），最后异步、并行上传并报字节数；打开快照先按清单 **预取**（`prefetch`，按 key 直达、不列目录），QGIS 再读内存。

**调试视图（`debug.js`）**

- 一个列表里看页面与 QGIS 两边的日志：页面的 `console.error/warn` 与未捕获异常、模块的 stdout/stderr（Qt、GDAL/PROJ）、QGIS 自己的消息日志（桥接事件 `log`）、每个工具调用的耗时、主线程 ≥100 ms 的卡顿、内存 / 线程 / 启动阶段，以及 pthread worker 崩溃的栈（给每个 `em-pthread` worker 套的 blob 前导负责转发）。
- 崩溃同时是一个页面状态：`window.qgisCrash`、事件 `qgis-crash`，页顶出现红色横条（Reload / Debug view / Copy report）；`qgis.call` 把之后的 `unwind` 与无回音改成一句明白话；报告存 localStorage，重载后列在第一条。
- 成本：环形缓冲 2000 条，关着时不渲染，只把错误数推到头部按钮。

**任务总线（`progress.js`）**

- 页面里所有耗时操作的唯一汇报处：`qgisProgress.begin(label)` → `t.set(detail)` / `t.update({ done, total, unit: 'bytes' })` / `t.finish()` / `t.fail()`，或 `run(label, fn)`。
- 谁在跑由各自的界面去听：工作区（开着时是头部下的进度条；关着时是按钮旁的药丸，150 ms 内结束的不闪）、加载页（还在时把最新任务当阶段行）、Debug 视图（每个任务一行 + 耗时）。
- 分享、打开快照、查询数据源（翻页数、Overpass 等待）、下载、应用链接的每一步都在这里。

**加载页（`loading.js` + `index.html`）**

- 按 `qgis.bundle.json` 数真实字节（克隆响应流计数，原响应保留 URL，Chrome 因此仍能缓存编译结果）、显示阶段、轮播解释原理，并展示 preset 里的链接。
- spinner 与强调色来自 `brand.js`（`window.qgisBrand`：名称、`--brand-accent`、`spinner()`；部署覆盖层可整文件替换），工作区复用同一套。
- `hold()`：带 `?share= / ?open=` 的链接会让加载页在 QGIS 起来后变成**半透明的幕**，显示快照下载进度，工程进来才退。

## 2. 扩展点：接新东西要改哪里

| 想做的事 | 改哪里 | 要不要编译 |
|---|---|---|
| 接一个**新的对象存储/文件服务** | `cloudfs.js` `registerBackend(type, impl)`（`list/read/size/write/remove/mkdir/copy`），preset `mounts` 里引用 | 否 |
| 接一个**内部数据查询服务**（OGC API Features、目录、返回 GeoJSON 的 HTTP API） | **一行 preset**：`"sources": [{ "name", "type": "ogcapi" \| "catalog" \| "geojson" \| "overpass", "url", … }]`；别的形状就 `qgisSources.registerType(type, { collections?, search?, fetch })`（一个 JS 文件，Web 插件里也能注册）。先例：`sources-overpass.js`（OpenStreetMap）；部署自己的网关同样是一个 Web 插件里的 `registerType()`——preset 里该类型的 `sources` 等它注册后自动接上，QGIS 零改动 | 否 |
| 给工作区头部加一个按钮 / 菜单项 | `window.qgisWorkspace.addAction({ id, title, icon, run })`（agent 自己的两个按钮就是这样加的）；菜单内容在 `workspace.js` 里按组维护 | 否 |
| 给工作区加一个**视图**（占用面板主体，像 Debug 那样） | `window.qgisWorkspace.registerView({ id, title, icon, render(el), onShow, onHide })`——头部多一个按钮，点开时替换 agent 的槽位；`debug.js` 是现成的例子（在 `ws-ready` 事件后注册） | 否 |
| 让 agent / 测试触发 QGIS 自己的菜单项 | `ui_trigger_action { id: "mActionAddOgrLayer" }`——先查 `ui_add_action` 登记的，再按 objectName 找 QGIS 的 QAction | 否 |
| 一个只有 agent 用的数据源（需要对话式检索） | 该服务提供 MCP 服务器，preset `agent.mcpServers`（docs/05 §4.4） | 否 |
| 新的 **URL 参数 / 分享内容** | `link.js` 的 `parse / build / apply / current` | 否 |
| 一个**耗时操作**要让人看见进度 | `const t = qgisProgress.begin('Doing X'); t.update({ done, total, unit: 'bytes', detail })；t.finish()`——不用碰任何界面代码，工作区 / 加载页 / Debug 视图自己会显示；云端大文件走 `qgisCloud.prefetch(items, { onProgress })` / `writeBehind(folder)` 就自带字节数 | 否 |
| 新的**页面工具**（给 agent / MCP / 插件用） | `qgis.registerTool(name, { description, inputSchema, run })`（Web 插件、技能、壳层都这样做） | 否 |
| 新的**业务能力**（导入向导、分析流程…） | agent 技能（`web/agent/skills/*.js`，docs/05 §5.1） | 否 |
| 新的 **QGIS 菜单入口** | 工具 `ui_add_action` + `action` 事件（Web 插件 / 壳层 / Python 插件共用） | 否 |
| QGIS 还没暴露的能力 | `qgswasmbridge.cpp` 加一个 `registerTool`（只增不改，docs/05 §3.3） | 是 |
| 新的 **preset 字段** | 页面消费的字段只改壳层；要 QGIS 消费的字段改 `qgswasmpreset.cpp` | 看字段 |

## 3. URL 方案（`link.js`）

所有参数可组合、都可省略；`?open=` 保持原有语义（经 QGIS 自己的 `openFile()`，工程替换当前工程，数据文件会走 QGIS 的对话框），其余由壳层直接调用工具完成，**没有对话框**：

| 参数 | 含义 | 例子 |
|---|---|---|
| `preset=<name>` | 部署 preset（`default` 可省略） | `?preset=team-a` |
| `open=<path\|url>[,…]` | 打开工程 / 文件（QGIS 的 openFile） | `?open=/cloud/shared/projects/<uuid>/x.qgz` |
| `share=<id>` | 打开云挂载上的一个**快照**：`<mount>/<prefix>/<id>/project.qgz`，并按其 `share.json` 的视野定位（`extent=` 可覆盖）。这是"Share a snapshot"复制的短链接；工程、数据、样式全部冻结。打开时加载页留作幕：先按清单预取全部文件（真实 MB 与速率），QGIS 再读内存并渲染第一幅视图，幕才退；`extent=` 与快照视野相同时不再二次渲染（第一幅还在解析大图层时改视野会让标签页停顿） | `?share=7f3c…` |
| `add=<path\|url\|source://…>`（可重复） | 直接加为图层：虚拟文件系统里的文件（`/cloud/…`、`/qgis/share/demo/…`，可带 `\|layername=`）、http(s) URL（先下载）、XYZ 模板、**查询数据源** | `?add=/cloud/gis/data/world_map.gpkg\|layername=countries&add=https://…/x.geojson&add=source://features/city_regions?limit=5` |
| `basemap=<name>` | preset 里的 XYZ 底图，放在最底层 | `?basemap=OpenStreetMap` |
| `crs=EPSG:xxxx` | 工程 CRS | `?crs=EPSG:3857` |
| `extent=xmin,ymin,xmax,ymax[@CRS]` | 缩放到范围（默认 EPSG:4326） | `?extent=-20,30,40,70` |
| `ask=<text>` | 页面就绪后交给 Web Agent | `?ask=Add OSM and zoom to Brazil` |
| `trace=1` / `force=1` | 调试输出 / 跳过浏览器预检 | |

应用顺序固定：工程 → 底图 → 图层（按 `add` 顺序，底到顶）→ CRS → 范围。

**分享**有三条路，都在页面层：

- `project_share`（工具 / agent / Plugins → Share → "Share project"）：把工程存到共享挂载的 `projects/<uuid>/<标题>.qgz`，链接 = `?preset=…&open=<路径>&extent=<当前范围>`，对方打开就是同一个工程、同一个视野。
- `view_link`（工具 / Plugins → Share → "Copy link to this view"）：**不保存工程**。工程本身在云挂载上就 `open=` 它；否则把"从任何浏览器都拿得到"的图层写进链接——云文件（含子图层）、URL（包括 agent 用 `layers_add` 直接加的 URL，壳层记住了它们的来源）、`source://` 查询、底图——再加当前范围。只在本浏览器里的东西（`/home/web_user`、内存图层）列在 `skipped` 里提示。
- 手工拼 URL：上表就是公开契约。

链接不再带 `index.html`，`preset=default` 省略，所以 `http://host/?add=…&extent=…` 这样的短链接就能用。

**两种链接，两种语义。** `share=<id>` 是**存储分享**：`project_share` 把工程和所有只存在于浏览器里的图层文件（查询结果、上传、下载、导出）复制进 `<mount>/projects/<id>/`，用 `layer_set_source` 把图层改指过去再保存，并写 `share.json`——打开者看到的和分享者完全一样，不依赖数据源当时的状态或权限；清单里记着每层的来源，所以 Share → "Refresh this snapshot from its sources"（`share_refresh`）能按原查询重跑、原地改写 `data/` 里的文件而不动样式。`add=source://…` 等参数是**配方分享**（`view_link`，"Copy a live link to this view"）：什么都不存，打开时重新查询，适合看实时数据和由 dashboard 等外部系统程序化拼链接。工程本身是快照时，`view_link` 返回的就是短链接。

## 4. 查询数据源（`sources.js`）

云挂载解决"像文件一样的数据"；查询数据源解决"要问一句才有数据"的服务。声明：

```json
"sources": [
  { "name": "features", "type": "ogcapi",  "title": "内部要素服务", "url": "https://geo.corp/ogcapi", "proxy": "auto", "limit": 2000 },
  { "name": "catalog",  "type": "catalog", "title": "数据目录",     "url": "https://data.corp/catalog.json", "search": "https://data.corp/search?q={q}" },
  { "name": "poi",      "type": "geojson", "title": "POI 查询",     "url": "https://api.corp/poi?bbox={bbox}&q={q}&limit={limit}", "headers": { "X-Token": "…" } }
]
```

| 类型 | 契约 | 适合 |
|---|---|---|
| `ogcapi` | `GET {url}/collections` → 集合；`GET {url}/collections/{id}/items?bbox=&limit=&q=` → GeoJSON | OGC API – Features 服务（pygeoapi、GeoServer、ldproxy、QGIS Server…） |
| `catalog` | `GET {url}` → `[{ name, title, description, url, format }]`（或 `{datasets|items|results}`），可选 `search` 模板做服务端检索；命中后用 `url` 经 `layers_add` 打开（GeoJSON / GPKG / GeoTIFF… 都行） | 数据目录、数据集清单 |
| `geojson` | `{url}` 模板里填 `{q} {bbox} {limit} {collection} {id}`，返回 GeoJSON | 任何"一问一答"的内部 API |
| `overpass`（`sources-overpass.js`） | 集合 = 常用标签预设（traffic_signals、crossings、stop_signs、motorway_junctions、roads、railways、buildings、parking、construction、tunnels_bridges）；`q` = 标签过滤（`highway=traffic_signals`、`amenity=cafe; shop`、`building`）或完整的 Overpass QL；bbox 必填（无 bbox 拒绝查询）→ `(s,w,n,e)`；`[out:json] … out body geom <limit>` 的结果在页面里转成 GeoJSON：node → 点、way → 线、闭合且带面属性的 way → 面、multipolygon relation → 面 | OpenStreetMap：公共 Overpass API `https://overpass-api.de/api/interpreter`（默认 preset 已配，请克制用量；自建镜像更好） |

有了声明，四个入口自动出现，不用配第二遍：

1. **工具**：`sources_list / sources_collections / sources_search / sources_load / sources_add`——Web Agent 的状态快照里有 `sources` 名单，提示词告诉模型"用户要的数据不在图上时先搜数据源"；MCP 客户端（Claude Code）和 Web 插件也直接可用。
2. **菜单**：Plugins → Data sources → "<title>…"，问一个集合/关键词，加载并缩放。
3. **链接**：`?add=source://<name>/<collection>?q=…&bbox=…&limit=…`；`view_link` 会把这样加进来的图层写回链接。
4. **代码**：`qgisSources.load('features', { collection: 'roads', bbox: [..] })`。

数据流：适配器返回 GeoJSON 文本 → 写到 `/home/web_user/sources/<源>/<名>-<时间>.geojson` → `layers_add`。QGIS 看到的只是一个文件。CORS：先直连，浏览器拦了就改走同源 `/proxy`（和 cloudfs 一样，`proxy: false` 可禁止）。

> 为什么不直接用 QGIS 自己的 WFS / OAPIF provider？这个 wasm 构建里 GDAL 没有网络驱动，QGIS 的 `wfs` provider 也没编（见 `build/qgis/src/providers`：只有 wms、wcs、arcgisrest、delimitedtext）。更重要的是：放在壳层，一个新服务 = 一行 JSON，不需要等 QGIS 支持它的协议。

## 5. 传输、缓存与服务器

| 文件 | 原始 | brotli（q9） | gzip | 何时下载 |
|---|---|---|---|---|
| `qgis.wasm` | 133.6 MB | 30.7 MB | 39.0 MB | 启动 |
| `qgis.data` | 18.8 MB | 2.9 MB | 3.9 MB | 启动 |
| `qgis.js` | 0.4 MB | ≈0.1 MB | ≈0.1 MB | 启动 |
| `world_map.gpkg`（`qgis.lazy.json` 所列的按需文件） | 12.9 MB | 4.5 MB | 9.1 MB | 首次读取（CRS 选择器预览等） |

- `scripts/compress-bundle.mjs` 在构建后生成 `.br` / `.gz` 旁路文件（`build-qgis.sh` 自动调用，约 25 s）；`serve.mjs` 在客户端接受该编码、且旁路文件不比原文件旧时发送它（`Content-Encoding` + `Vary: Accept-Encoding`，ETag 带编码后缀）。首次加载从 ≈166 MB 降到 ≈34 MB（gzip ≈43 MB）。浏览器只在安全来源（https / localhost）上声明 `br`，LAN 的 http 回落到 gzip。
- 验证策略不变：`Cache-Control: no-cache` + ETag，每次加载都 304 一次（qgis.js 与 qgis.wasm 必须成对，不能各自按 max-age 缓存，见 serve.mjs 注释）。`tests/e2e/warm.py` 证明这条路是通的：同一浏览器档案第二次打开，三个文件各只传 300 B 校验头，Chrome 连编译结果一起复用，主窗口 ≈1.0 s；加载页记录的"下载完成 → 模块就绪"冷 4.8 s、热 0.13 s，差的就是编译。部署到别的服务器时保住这两样（`application/wasm` 的 Content-Type、`no-cache` + ETag），热启动就还在。
- 多人共用一台服务器时 `serve.mjs --shared`（`scripts/deploy.sh` 默认这样装）：MCP / agent 调用必须带 `?client=<页面 id>`（页面 id 由页面自己随机生成、只有它知道，Plugins → Share 里可复制自己的端点），`/agent/result` 只接受该页面的回复，`/agent/clients` 关闭，`/proxy` 只到 preset 里出现过的主机（加 `--proxy-allow`），重定向也逐跳检查。这些都在页面层/服务器层，QGIS 不知道有多少人在用它。`tests/serve-shared.test.mjs` 覆盖。
- 换成 nginx：`brotli_static on; gzip_static on;` 加两条头即可，页面层无需改动：

```nginx
location / {
  add_header Cross-Origin-Opener-Policy same-origin always;
  add_header Cross-Origin-Embedder-Policy credentialless always;
  brotli_static on; gzip_static on;
  types { application/wasm wasm; }
  etag on;
}
```

- **按需文件**：很少用到的大资源不进 `qgis.data`。`cmake/QgisWasmApp.cmake` 的 `QGIS_WASM_LAZY_FILES`（`源文件@虚拟文件系统路径`，默认只有 `resources/data/world_map.gpkg`——12.9 MB，只有 CRS 选择器的预览地图和状态栏彩蛋会读）把文件从打包里排除、复制到 `qgis.js` 旁边，并写出 `qgis.lazy.json`（文件名、大小、虚拟路径）。页面启动时用 `cloudfs.js` 的 `http` 后端把这些文件只读挂在 `/qgis/share/qgis/lazy`（内部挂载，不出现在挂载列表），再用符号链接把原路径指过去：QGIS 仍然打开原来的路径，字节在第一次读时才取——整文件一次 GET、不带 Range，所以服务器能直接发 `.br`。再加一个文件只需在 cmake 列表里多写一项，页面层与 QGIS 都不用改。剩下的大头 `proj/proj.db`（10.2 MB）启动就要读，不适合按需。

## 6. 浏览器兼容

`index.html` 在加载任何 wasm 之前做预检：缺 **JSPI**（`WebAssembly.Suspending`）或 **SharedArrayBuffer / 跨源隔离**时显示一页说明（缺什么、为什么需要、怎么办：换浏览器 / 走 HTTPS 或 localhost / 服务器加 COOP+COEP 头），什么都不下载；`?force=1` 跳过（给 asyncify 构建用）。

| 浏览器 | 状态（2026-10） |
|---|---|
| Chrome / Edge ≥ 137 | 可用（JSPI 自 137 默认开启） |
| Safari 27+ | JSPI 已随 Safari 27 到来，需在实际设备上验证 |
| Firefox | JSPI 尚未默认开启（计划 153；Nightly 可通过 `javascript.options.wasm_js_promise_integration` 打开） |

需要 Firefox 时的退路是 `cmake -DQGIS_WASM_NESTED_LOOPS=asyncify` 另构建一份（更大更慢，docs/01）。

## 7. 性能现状与方向

已测（docs/01 §3、docs/05 §8、`agent.py`/`features.py` 日志）：主窗口 3–8 s，demo 工程渲染 10–16 s（SwiftShader 下偏慢），每个工具调用 < 0.3 s，页面主线程无 > 300 ms 卡顿；agent 的慢在网关首字节 2–4 s × 来回次数（已把常见任务压到 2 个来回）。接下来按收益排序：

1. 传输：已做（本文 §5）。部署到 CDN/nginx 时记得旁路文件和两条头。
2. `-DQGIS_WASM_PROFILING_FUNCS=OFF`：wasm 小 15 MB（压缩后约 3 MB），代价是栈里没有函数名；发布构建可开。
3. `qgis.data` 按需：已做（§5），`world_map.gpkg` 不再随启动下载，启动少解压 13 MB 进内存。
4. 启动：Qt 线程池预热与 QGIS 初始化已优化（docs/02 §2.4）。wasm 编译不是瓶颈：32 核机器上，浏览器档案放在 tmpfs 时冷启动（下载 34 MB + 编译 + 初始化）主窗口 1.4 s；同一档案第二次打开 1.0 s（每个文件只传 300 B 校验头，编译结果来自 Chrome 的代码缓存）。测试机上冷启动看起来要 8–13 s，全部是 Chrome 往 ext4 磁盘写新档案和缓存（约 50 MB）的 I/O，与 wasm 无关——同一次测量换到 /dev/shm 就是 1.4 s。所以首次打开的体验取决于用户磁盘，服务端能做的（压缩、按需文件、可缓存）已经做完。
